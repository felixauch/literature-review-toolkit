# CSV storage, backups and transfer

Developed with assistance from GPT-6 Astra. Documentation generated by GPT-6 Astra.

All review decisions, evidence selections and their revision history are CSV-backed. No SQL database is created or required for a new review. JSON remains useful for settings, provider caches, handoff reports and derived browser data; it is not the decision store.

| File or folder | Purpose |
|---|---|
| `manifest.csv` | Prepared-run metadata, source paths, hashes and settings snapshot. |
| `classification/catalog.csv` | Prepared category and domain suggestions, separate from decisions. |
| `classification/classification.csv` | All saved classification revisions. |
| `extraction.csv` | All saved evidence-form revisions, including supporting entries. |
| `domain_notes.csv` | Domain synthesis notes and revisions. |
| `reading.csv` | Reading-plan revisions, when enabled. |
| `*_current.csv` | Derived current-state view, regenerated from the history. |
| `*.backup.csv` | Previous committed journal file, overwritten by the next save. |
| `papers/*.csv`, `paper_sections/*.csv` | Locally extracted page text and detected sections. |
| `*.project.json`, `reading_plan.json` | Configuration and optional reading rules. |

The history files use typed column names to preserve nested notes, lists, missing values and text exactly. Text cells are escaped for spreadsheet safety and decoded by the toolkit. Do not edit these internal files in a spreadsheet: use the review form. Export ordinary summary CSVs for analysis. Invalid checksums stop loading instead of silently accepting damaged records.

## Saving and backups

A save checks the expected revision, writes a complete temporary file and atomically replaces the journal. Competing saves are rejected rather than overwriting newer work. The current-state view can be rebuilt from history. A previous-file backup helps recovery but is not a substitute for dated backups of the whole run.

Use **Export all review CSVs + history ZIP** in Export & help. The export includes the run CSVs and JSON settings while blocking journal writes briefly. It does not include PDFs stored elsewhere, original database exports, virtual environments or source CSVs outside the run. Keep those separately. Work on one computer at a time; a cloud-sync service cannot coordinate simultaneous edits safely.

## Continue an older review

Stop its server first. In the setup page, choose **Open saved review** and select the old run folder. The toolkit reads old SQLite/JSON records without editing them, creates a separate `-csv` sibling folder and opens that converted copy. Keep the original as a backup. Migration preserves labels, states, history and the recorded origin of decisions; it does not confirm papers or change scientific judgments.

A `migration_report.csv` records source hashes and conversion details. Historical evidence hashes remain in history; a migration snapshot updates the current file hash where the prepared evidence file changed format. Compare record counts and representative saved forms before continuing. If a target already exists, open that converted run or choose another output folder with the migration command; no existing run is overwritten.

## Read-only corpus explorer

Choose **Export corpus explorer ZIP**. Extract it and open `Corpus explorer.html` in your browser. It embeds the summary CSV so it needs no Python, server or database. Its filters, paper views and clickable maps use the same code and style as the live toolkit. A copy of the CSV and project settings accompanies it. `Load CSV` opens a newer compatible summary in memory; it does not write your project.

The summary does not contain source PDFs, abstract/conclusion text, full quotations or revision history. Missing labels are not invented as No. Saved states remain as exported. Use the editable toolkit and original PDFs to check or change them. For different field definitions, export a new browser from that configured review.
